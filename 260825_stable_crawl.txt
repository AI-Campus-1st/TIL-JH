크롤러-안정성 엔지니어링

1. Probability : 드문 일이 반드시 일어난다
2. Time : 시간이 길어진다.
3. Cost : 수집된 자료가 날아가면 다시 하기 어렵다.

- 실제로 겪는 실패
1) ConnectionError : 상대 서버가 잠시 끊었거나 내 네트워크가 흔들렸습니다.
2) Timeout : 응답이 오지 않습니다. timeout이 없으면 여기서 영원히 멈춥니다.
3) 429 Too Many Requests : 너무 빨리 보냈습니다. 속도를 줄이라는 신호
4) AttributeError:NoneType : 그 페이지에만 없는 항목, 한 건 때문에 전체가 멈춘다.
5) UnicodeDecodeError : 인코딩이 다른 페이지가 섞여 있습니다.

※ 오늘의 목표 : 많이 모으는 것이 아니라, 끝까지 가는 것
 - 중간에 실패해도 전체가 멈추지 않는다.
 - 무엇이 왜 실패했는지 나중에 확인할 수 있다.
 - 멈춘 지점부터 이어받을 수 있고, 다시 돌려도 중복이 생기지 않는다.

만약 한 파일에 다 쓰면, 
(목록과 상세가 붙어 있으면 생기는 문제)
-> 상세 수집이 실패하면 목록 수집 결과도 함께 날아간다.
-> 어디까지 했는데 알수 없어 처음부터 다시 돌려야 합니다.
-> 목록만 다시 훑고 싶어도 그럴 수 없다.

for page in range(1, 101):
    for url in get_list(page):
        detail = get_detail(url) # 만약 여기서 죽으면, 앞의 99페이지 목록도 함께 사라짐
        save(detail)

=> 그렇기 때문에, 목록과 상세를 독립된 작업으로 나눈다.
1. 목록 수집 : 페이지를 훑어 URL만 모은다.
2. URL 큐 : 파일 또는 DB에 상태와 함께 저장
3. 상세 수집 : 큐를 읽어 하나씩 처리
4. 결과 저장 : 성공은 결과로, 실패는 실패 큐로

※ URL 큐 설계(주소만 담지 말고 상태를 함께 담습니다.)
 - 상태 컬럼 하나로 재개/재시도/통계가 모두 해결된다.
 - pending만 골라 돌리면 그것이 곧 이어받기가 된다.

```
# urls.csv
url,status,tried,collected_at
https://.../1,pending,0,
https://.../2,done,1,2026-08-06 21:10
https://.../3,failed,3,

# status : pending → done | failed
# tried  : 시도횟수— 상한을넘으면포기
```

※ 예외 다섯 갈래
1) Timeout(응답이 오지 않음) : 재시도-일시적일 가능성 높음
2) ConnectionError(연결 자체가 실패) : 재시도-간격을 두고
3) HTTP 4xx(요청이 잘못됨) : 재시도 무의미-기록하고 건너뜀
4) HTTP 5xx(서버 문제) : 재시도-백오프 필수
5) 파싱 실패(구조가 다름) : 기록하고 건너뜀-나중에 원인 분석

※ try는 반복문 안에 걸자
•     반복문“안”에try를두는것이원칙입니다.
•     except Exception: pass 는절대쓰지마세요—  침묵하는버그 가됩니다.
•     요청과파싱을분리해잡으면원인구분이쉬워집니다

# 나쁜예—  전부한덩어리 try:
for url in urls:
...
except Exception:
pass          #  무엇이실패했는지모릅니다

# 좋은예—  한건단위로
for url in urls:
try:
process(url) except Exception as e:
log_and_skip(url, e)

※ 로그 레벨 설계(무엇을 어느레벨로 남길지)
DEBUG(평소엔 안 보고 싶은 것) : 요청 URL, 응답 크기
INFO(정상 진행 상황) : 페이지 완료, 누적 건수
WARNING(실패했지만 계속 감) : 한 건 파싱 실패, 재시도
ERROR(멈춰야 할 문제) : DB 연결 실패, 인증 오류

※ 체크 포인트 세 가지 방법(어디까지 했는지 어떻게 기억할 것인지)
방법1) 진행 파일
-> 마지막 페이지 번호를 파일에 씁니다. 가장 간단하지만 순차 수집에만 통합니다.
방법2) 상태 컬럼
-> 큐의 각 행에 done/pending을 표시합니다. 순서와 무관하게 재개할 수 있어 가장 실용적입니다.
방법3) 수집완료 목록
-> 이미 저장된 결과에서 키를 읽어 제외합니다. 별도 관리가 필요 없지만 결과가 커지면 느려집니다.
