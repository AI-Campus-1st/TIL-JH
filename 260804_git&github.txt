git & github 특강 - 박성훈 강사님

- git에 대한 기본적인 설명 및 설치방법

- github에 있는 파일이 원본[origin]이고, 다운로드 -> 작업 -> 원본을 재업로드
- github에 공유
  - 최초생성(첫 다운로드) : Clone
  - 업로드 : Push
  - 다운로드 : Pull

commit -> Pull받아서 작업 -> github에 Push ( -> 동료가 Pull해서 작업 -> 동료가 다시 Push )


나의 local commit 버전을 가리키고 있음 : main(파란색)
github 버전을 가리키고 있음 : origin/main(보라색)
=> 내 commit이 최신버전인지 구버전인지 확인가능

squash 3 commit -> 커밋3개를 하나로 합치는 기능



branch는 새로운 버전의 소스코드를 만드는 것 (main소스코드를 안전하게 지키기 위한 방법)

create branch from commit : 선택한 commit으로 새로운 branch를 만드는 기능
=> 과거의 commit시점을 기준으로 branch(곁다리)를 만들 수 있음


**브랜치 합치는 방식(4가지)

1. Fast-forward (가장 기본방식) : 갈라진 기록이 없을 때, 그대로 두개가 합쳐짐
ex. 1,2까지는 main브랜치, 3,4,5가 test01브랜치라면 =>합치면서 1,2,3,4,5가 된다.
-> 메뉴에는 없지만 갈라진 기록이 없다면 자동으로 이방식을 채택

2. Create a merge commit : 모든 이력을 남기며 Merge 됨을 새로운 Commit으로 남김
(장점)아주꼼꼼하게 기록된다. (단점) 추적하기 복잡하다.
-> 아주 중요한 작업을 하는 경우

3. Squash & Merge
 : 합치고자 하는 브랜치의 내용을 압축하여 하나의 Commit으로 남김
(장점)main브랜치 하나만 남김 (단점) 3,5,7의 상세내역이 날아감
-> 소소한 작업 여러개일때, 하나로 합쳐서

4. Rebase (현업에서 많이 사용) : 합치고자 하는 브랜치의 Commit들을 Main branch의 재 배열하여 Merge
(장점)심플+상세내역도 남음,
-> 커밋주소값이 바뀜


**Branch 전략 (대표적인 3가지 소개)
1. Gitflow
 - 5개의 Branch를 활용하여 소스코드 관리
 - feature단위기능개발 -> dev브랜치로 머지 -> 배포를 위해 main으로 가기 전에 QA하기위해 release브랜치로 머지-> 최종적으로 main브랜치로 머지하여 고객에게 배포
 - main배포했는데 긴급 버그 수정시 dev -> hotfix브랜치 -> main으로 Merge

2. Github flow
 - main브랜치가 최종 소스코드로서 항시 배포 가능한 상태
 - 작업 완료되면 바로 main으로 합치기 때문에, 합치기 전에 Code review(중요)필수적으로 진행
 - 웹 서비스에 적합한 형태로 수정된 부분이 상시 배포가 가능한 서비스에 적합한 형태

3. Gitlab flow
 - Gitflow와 github flow의 중간 느낌
 - main브랜치를 중심으로 개발 진행(github flow와 비슷)
 - 버그가 발생해도 일단 main에서 수정
 - 그러나 배포전에 PP와 배포브랜치(Production branch활용)


Repository의 Issues (해야 할 일)
-> 이번주에 해야 할 일을 PM이 등록을 하고, 일 시작~끝날때까지 모든과정을 기록
-> 매번 Issue의 티켓을 만들고, 담당자를 지정하고, 댓글로 상황을 공유하고, Deadline을 지정하고 등등


pull request (코드검증, 리뷰)
-> 별도의 branch가 commit되면, 검증을 추천하는 노란박스가 나온다.
-> pull request 또한 Issue다.


project, milestone, issue로 관리하며 동료들과 협업을 진행.


해야할일list는 -> Backlog
그중 진짜 해야할 준비 할것 -> Ready
프로젝트 중인것들 -> In progress
